## Description

The `WordPressPublisher` service in `src/services/wordpress_publisher.py` makes external HTTP calls to WordPress REST API endpoints for publishing posts, managing tags, validating plugin connections, and updating posts. None of these HTTP calls have retry logic, meaning any transient network failure (DNS timeout, connection reset, 502/503 from WordPress, rate limiting with 429) causes an immediate failure with no recovery attempt.

This is particularly problematic because WordPress sites are external systems with variable reliability — shared hosting can return 503 during traffic spikes, CDNs can return 502 during cache misses, and WordPress maintenance mode returns 503. Without retry logic, content that was successfully generated by the AI pipeline fails at the final publishing step, requiring manual user intervention to retry.

The project already uses `tenacity>=8.2.0` as a dependency (declared in `pyproject.toml` line 50) and has established retry patterns in two other files: `src/flow/engines/serp/fetch_serp.py` (lines 12-17) uses `@retry` with `stop_after_attempt(3)`, `wait_exponential(multiplier=1, min=4, max=10)`, and `retry_if_exception_type((httpx.RequestError, httpx.TimeoutException))`. The `src/services/email_service.py` (lines 254-258) uses a similar pattern with `before_sleep_log` for logging retries. The WordPress publisher should follow the same established pattern for consistency.

Tenacity 8.2+ natively supports async functions — the `@retry` decorator automatically detects `async def` and uses `asyncio.sleep` (not `time.sleep`) between retries, so it does not block the event loop. No special async configuration is needed.

The four methods that need retry logic are: `validate_plugin()` (line 76), `publish_post()` (line 100), `_get_or_create_tags()` inner calls (line 207), and `update_post()` (line 250). However, the retry should only apply to transient errors — it should NOT retry on 4xx client errors (except 429 Too Many Requests) since those indicate a permanent problem like invalid credentials or malformed data.

## Why This Matters (Context & Reasoning)

Content publishing to WordPress is the final step in the Rext AI content pipeline. If it fails, the user's AI-generated content is stuck in an unpublished state. Users connecting external WordPress sites are often on shared hosting or managed WordPress platforms where transient 5xx errors and timeouts are common. Without retry logic, every transient failure becomes a user-visible error requiring manual retry. The content generation process itself (AI pipeline) is costly in terms of time and API credits, so failing at the publishing step wastes all that upstream work.

The risk of NOT fixing this includes: increased user frustration, wasted AI generation credits, and support tickets about "publishing always fails." Adding retry with exponential backoff is an industry-standard resilience pattern for external API integrations, and the project already uses it for other external calls (Serper.dev API, email service).

---

## Impact

- **Severity:** Content publishing fails silently on transient network errors. Users must manually retry, with no guarantee the next attempt will succeed either.
- **Affected Users/Flows:** All users who publish content to connected WordPress sites. The `publish_to_site` endpoint in `sites.py` and `_publish_to_all_sites` in `publish_content.py` both create `WordPressPublisher` instances and call these methods.
- **Blast Radius:** Affects all WordPress publishing operations including: single-site publish, multi-site publish, plugin validation during site connection, and post updates.

## Recommended Solution

### Step 1: Add tenacity imports and define retry predicate

```python
# File: rext-backend/src/services/wordpress_publisher.py
# Add to imports at the top (after line 3):

import logging
import os
import httpx
from typing import Dict, Optional
from tenacity import (
    retry,
    stop_after_attempt,
    wait_exponential,
    retry_if_exception,
    before_sleep_log,
)
from src.api.schema.content_schema import ContentCreate, ContentUpdate, ContentResponse

logger = logging.getLogger(__name__)


def _is_retryable_error(exception: BaseException) -> bool:
    """Determine if an exception is retryable (transient network/server errors)."""
    if isinstance(exception, httpx.TimeoutException):
        return True
    if isinstance(exception, httpx.ConnectError):
        return True
    if isinstance(exception, httpx.HTTPStatusError):
        return exception.response.status_code in (429, 500, 502, 503, 504)
    return False
```

### Step 2: Add retry decorator to `validate_plugin()`

```python
# File: rext-backend/src/services/wordpress_publisher.py
# Replace validate_plugin method (lines 76-98):

    @retry(
        retry=retry_if_exception(_is_retryable_error),
        stop=stop_after_attempt(3),
        wait=wait_exponential(multiplier=1, min=2, max=10),
        before_sleep=before_sleep_log(logger, logging.WARNING),
        reraise=True,
    )
    async def validate_plugin(self) -> bool:
        """
        Validate the Rext-AI WordPress plugin connection.

        Returns:
            True if valid, raises an exception if invalid.
        """
        endpoint = self.api_endpoint if self.api_endpoint else f"{self.site_url}/wp-json/rext-ai/v1/"

        try:
            response = await self.client.get(endpoint, timeout=15)

            if response.status_code == 200:
                return True
            else:
                error_msg = f"Rext-AI validation failed (Status {response.status_code}): {response.text}"
                logger.error(error_msg)
                raise Exception(error_msg)

        except httpx.HTTPError as e:
            error_msg = f"Failed to connect to Rext-AI plugin at {endpoint}: {str(e)}"
            logger.error(error_msg)
            raise
```

### Step 5: Fix exception re-raising in `publish_post` and `validate_plugin`

The current code catches exceptions and raises new generic `Exception` instances, which breaks the exception chain and prevents tenacity from seeing the original retryable exception type. Fix the exception handlers to re-raise the original exception:

```python
# File: rext-backend/src/services/wordpress_publisher.py
# In publish_post, replace the except blocks (lines 195-205):

        except httpx.HTTPStatusError as e:
            error_msg = f"WordPress API error: {e}"
            if e.response is not None:
                error_msg += f" - {e.response.text}"
            logger.error(error_msg)
            raise  # Re-raise original exception for tenacity to evaluate

        except httpx.TimeoutException as e:
            logger.error(f"WordPress API timeout: {str(e)}")
            raise  # Re-raise for tenacity retry

        except httpx.ConnectError as e:
            logger.error(f"WordPress connection error: {str(e)}")
            raise  # Re-raise for tenacity retry

        except Exception as e:
            error_msg = f"Failed to publish to WordPress: {str(e)}"
            logger.error(error_msg)
            raise  # Non-retryable, will exhaust retries and re-raise
```

2. Attempt to publish content.
3. Observe in logs: tenacity logs WARNING messages for each retry attempt with exponential backoff timing.
